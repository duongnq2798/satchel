Satchel's security doesn't rest on one mechanism. A locked contract, a record written before every signature, a
sale that pins what the buyer checked, a report read at finalized blocks, and guards in the app and the CLI each
close a different way to cheat. This page lists each layer with the code that enforces it and the tests that pin
it down, then says plainly what Satchel trusts and what it does not claim.

<Callout type="danger" title="Not audited">
No third party has reviewed this code. Two internal reviews of the contract, one of them adversarial, found two ways to slip an
approval past the first version of the record, then two smaller gaps in the fix; all four are fixed and covered by
tests. On mainnet a satchel holds real funds: keep in one only what you can afford to lose.
</Callout>

## Layers

<ArchitectureDiagram />

| Layer | What it enforces | Code | Tests |
| --- | --- | --- | --- |
| Locked contract | No access keys, no admin, no upgrade method: nobody, the deployer included, can redeploy it or sign as it. `new` is private and ran in the deploy transaction | `new` in `contracts/satchel/src/lib.rs`, `tools/deploy-mainnet.sh` | `scripts/check-claims.mjs`, on chain |
| The contract builds what it signs | Every `sign_evm` signature is over an EIP-1559 transaction the contract RLP-encoded and hashed itself; anything else goes through `sign_raw` and is counted as opaque | `Eip1559Tx::signing_hash` in `evm.rs` | `evm_hash_and_rlp_match_viem_for_every_vector`, `evm_signing_hash_view_matches_the_hash_sign_evm_sends` |
| Record first | The record is saved in the `sign_evm` receipt; the MPC `sign` call is a later receipt, so nothing that happens to it can undo the record | `sign_evm`, `sign_raw`, `request_signature` in `lib.rs` | `sign_evm_calls_mpc_with_the_token_path_and_records_the_nonce`, `sign_raw_counts_as_opaque`, `a_sale_in_the_middle_of_a_payout_keeps_the_send_on_record` |
| Every call classified | Value transfer, asset transfer, approval, revocation or unclassified; selectors are checked against the keccak of their signatures | `Eip1559Tx::classify` in `evm.rs` | `value_and_asset_transfers_are_classified`, `a_call_satchel_cannot_classify_is_counted`, `revocations_are_logged_but_never_take_an_approval_slot`, `approval_selectors_are_the_keccak_of_their_signatures` |
| Approvals itemized, then counted | 32 distinct approvals listed per token; beyond that, counted, never dropped. At the caps, a listed satchel takes 8,558 of the 10,000 bytes its mint paid for | `sign_evm`, `MAX_APPROVALS`, `MINT_DEPOSIT` in `lib.rs` | `approvals_beyond_the_cap_are_counted_not_dropped`, `erc721_approvals_of_two_token_ids_stay_two_rows`, `a_record_at_the_caps_and_its_listing_fit_in_the_mint_deposit` |
| Owner only; listing freezes signing | Only the current owner signs, with 1 yoctoNEAR and at least 50 TGas, and never while listed | `assert_can_sign` in `lib.rs` | `sign_evm_refuses_a_non_owner`, `sign_evm_is_frozen_while_listed`, `sign_raw_is_frozen_while_listed`, `the_previous_owner_cannot_sign_after_a_transfer`, `the_seller_cannot_sign_while_their_payment_is_in_flight` |
| `buy` pins what the buyer checked | The record version and the price must be the ones the buyer names | `buy` in `lib.rs` | `buy_refuses_a_stale_record_version`, `buy_refuses_after_the_seller_delists_signs_and_relists`, `buy_refuses_a_changed_price` |
| Any transfer ends the listing | `nft_transfer`, `nft_transfer_call` and a bounced transfer each void the listing, and only the owner can transfer | `nft_transfer`, `nft_transfer_call`, `nft_resolve_transfer`, `active_listing` in `lib.rs` | `nft_transfer_ends_the_listing_and_moves_signing_rights`, `a_transfer_cancels_the_sale`, `nft_transfer_call_ends_the_sellers_listing`, `a_bounced_transfer_call_voids_the_receivers_listing`, `a_non_owner_cannot_nft_transfer_the_token` |
| A fixed chain list | Only the 16 chain ids in `SUPPORTED_CHAINS` can be signed for, so every record is checkable | `SUPPORTED_CHAINS` in `evm.rs` | `sign_evm_refuses_an_unsupported_chain`, `every_supported_chain_can_be_signed_for` |
| The four checks | Each chain read at a finalized block; anything unreadable is "unknown", never a pass | `contractCheck`, `pendingCheck`, `approvalsCheck`, `countersCheck` in `packages/satchel-nft/src/report.ts`; `approvals.ts` | `report.test.ts`, `approvals.test.ts` |
| App and CLI guards | No address and no signature until the network's contract passes check 1; only this network's contract, from an account on this network; no transfer to an account that doesn't exist | `assertDeployment`, `assertTxFor`, `assertReceiver` in `packages/satchel-nft/src/guard.ts` | `guard.test.ts` |
| Check before broadcast | A send checks that the contract's `evm_signing_hash` equals viem's hash of the same transaction, and that the MPC signature recovers to the satchel's address, before it broadcasts | `sendFromSatchel` in `packages/satchel-nft/src/send.ts` | `send.test.ts` |
| CLI signing | The near CLI only signs. `satchel-nft` runs it by its absolute path, decodes what it signed, compares signer, receiver, method, arguments, gas and deposit with what it asked for, shows it, and sends only after `yes` or `--yes` | `resolveNearCli`, `decodeSignedTx`, `assertSignedAsAsked` in `near-cli.ts`; `submit` in `cli.ts` | `near-cli.test.ts`, and on testnet (`deployments/testnet-cli.json`) |
| The holder room's gate | A NEP-413 signature over a message the server writes itself, at most 5 minutes old; a full-access key of the account and the account as the satchel's owner, both read at one final NEAR block, on every request | `checkHolder` in `holder.ts`, `verifyNep413` in `nep413.ts`, `web/src/app/api/room/route.ts` | `holder.test.ts`, `nep413.test.ts` (against vectors near-cli-rs signed), `room-request.test.ts` |

## What a dishonest seller can try

| The seller tries to | and | Shown by |
| --- | --- | --- |
| Keep a signed withdrawal and broadcast it after the sale | Check 2 fails: a nonce was signed that is not yet spent at a finalized block | Satchel #5 on testnet |
| Approve an address of their own to spend the wallet's tokens | Check 3 fails: the allowance is still granted on chain | Satchel #3 on testnet |
| Have something signed blind (a permit, a Bitcoin transaction) | Check 4 fails: the opaque signature is counted | Satchel #6 on testnet |
| Hide an approval in a multicall, or push one past the 32nd row | Check 4 fails: the call is unclassified, or the approval counted | Unit tests |
| Sign while the satchel is listed | The contract refuses | [`5ZaKqJUx…`](https://testnet.nearblocks.io/txns/5ZaKqJUxEUauvpENMMp4KQoCwWRNqmAyHskpTF6Axft8) |
| Delist, sign and relist after the buyer checked | `buy` fails and the buyer keeps their NEAR | [`7HQPu9qe…`](https://testnet.nearblocks.io/txns/7HQPu9qeJauNrJLaMNCUuMJVska3u3uYsoGyp7gsCfWv) |
| Keep signing after the sale | Refused: only the token's owner can sign | [`GqFsnmFL…`](https://testnet.nearblocks.io/txns/GqFsnmFLcpDjJVC1b4qUPYxHRTP1Rw2vcVKxga3PVRvU) |
| Swap the contract's code, or sign as the contract | Not possible: the account has no keys, and check 1 would fail if it had | `node scripts/check-claims.mjs` |

You can run the first three yourself in [Try to cheat a buyer](/docs/tutorials/try-to-cheat-a-buyer).

## The holder room

The [holder room](/docs/guides/holder-room) is a page only a satchel's current holder can open. Its contents are
public, so what it protects is the gate. `/api/room` stores nothing between requests.

| Someone tries to | and | Shown by |
| --- | --- | --- |
| Replay a signed proof they saw | It opens only the room it names, for 5 minutes after its `Issued` time (which may be a minute ahead of the server's clock), and only while that account still owns the satchel | `holder.test.ts` |
| Open the room with a function-call key, the login key a site keeps | Refused (403): the key must be a full-access key of the account at the final block | `holder.test.ts` |
| Open the room as a former holder, after a sale | Refused (403), naming the owner at the final block. A final block is a few seconds behind the chain's head | `holder.test.ts` |
| Forge a signature, or reuse one made for another site or message | Refused (401): strict ed25519 over the NEP-413 payload the server builds, with recipient `satchelnft.xyz` | `nep413.test.ts`, against two vectors near-cli-rs signed |
| Run a NEAR RPC that lies about the key or the owner | Not stopped: the server reads one NEAR RPC, FastNEAR's by default, and can be fooled into opening or closing the room. Every read is pinned to one block | [Threat model, row 27](/docs/security/threat-model#the-holder-room) |

## What Satchel trusts

- **NEAR's consensus and runtime**, including that a `#[private]` method and a deleted key behave as specified.
- **NEAR's MPC network** (`v1.signer` on mainnet, `v1.signer-prod.testnet` on testnet). It signs for a key derived
  from the calling account and a path, only when that account asks. If enough MPC nodes colluded, they could sign
  with any derived key, and Satchel can't detect that. The MPC contract can also be upgraded by a vote of its
  participants, which could change how keys are derived or who may ask for a signature.
- **Each EVM chain's finality.** Once a block is finalized, an address's nonce at that block can't go back.
- **The pinned build image** behind the reproducible build, `sourcescan/cargo-near:0.22.0-rust-1.99.1`.
- **The RPCs the reader picks.** The report names them; `satchel-nft verify` can use your own.
- **The NEAR RPC behind the holder room**, which decides only who opens the room. The room holds nothing secret.
- **The npm release**, for anyone who runs `npx satchel-nft` instead of the repository's code. Version 0.2.0 was
  published without npm provenance; the [threat model](/docs/security/threat-model#what-satchel-trusts) says how
  to check its files against commit `2dd4209`.

## What Satchel does not claim

- **It is not audited.** Internal reviews only.
- **The report proves only what the token's key signed.** It says nothing about powers built into an asset: an
  upgradable token, a blacklist, an issuer's clawback, an ENS name whose controller is still the seller.
- **The report trusts its RPCs**: one NEAR node and one node per EVM chain. It doesn't compare nodes or check
  storage proofs. A lying RPC you chose can make a satchel look clean.
- **The hosted app is trusted** by anyone who doesn't run `satchel-nft verify` themselves or read their wallet's
  prompt. The wallet shows each call, its arguments and its deposit before you sign.
- **Limits are permanent.** The chain list and the 32-approval cap can't change, there is no admin to return NEAR
  stuck after a failed seller payment, and a testnet that shuts down leaves its satchels unprovable for good.
- **`PROVABLY CLEAN` is not AML-clean.** It means nothing the seller can still sign, and says nothing about where
  the funds came from.

Out of scope: the MPC network's own security, the wallets that sign NEAR transactions, and phishing (a page that
imitates satchelnft.xyz, or another contract called "Satchel"; the report reads only `v1.satchel-nft.testnet` or
`v1.satchel-nft.near` and checks its code hash).

The [threat model](/docs/security/threat-model) goes through every attack (the seller's, a buyer's, the
deployer's, an RPC's, the hosted app's, and on the holder room), what stops it, and what is left, ending with
[residual risks in one list](/docs/security/threat-model#residual-risks-in-one-list).

## When something fails

The threat model covers attacks. These are failures of a key, a network or a service Satchel depends on, and what
the holder or a buyer can do. Each answer holds for the locked contract, which no one can change.

| When | What happens | What to do |
| --- | --- | --- |
| The holder loses their NEAR key | Satchel can't recover it: there is no admin and no recovery method, and no account but the owner can have the contract sign for the satchel, list it or transfer it. What its address holds stays out of reach. A listing stays open, and its price goes to the account no one can use | Keep a second full-access key on the account, or have a DAO own a satchel worth much ([A satchel owned by a Sputnik DAO](/docs/tutorials/dao-owned-satchel)) |
| The key is stolen | To the contract, a stolen full-access key is the holder: the thief can empty the address on every chain, list the satchel or transfer it. A function-call key, the login key a site adds, can do none of these, since each needs a deposit | Transfer the satchel to a safe account and delete the stolen key; whichever transaction lands earlier wins. Every signature the thief gets stays in the record |
| NEAR's MPC network halts or is slow | The record is saved before the MPC call, so a request that fails or times out still counts its nonce, and the satchel reads <Verdict v="not-provable" /> until a transaction at that nonce is final. A timed-out request can still produce a signature later. Nothing can be signed while the network is down; transfers, listings, sales and the report don't call it | Once it answers, [send](/docs/guides/send) again: the app reads the next nonce from the chain, which is still that one. A buyer waits for check 2 to pass |
| NEAR halts | Nothing can sign, move or sell until NEAR runs again, and no new signature can be made for any address. What was signed or approved before the halt can still be used on its chain: anyone can broadcast a signed transaction that was never sent, since its signature is public, and a live approval can still be spent | Wait, and don't buy a satchel whose signed nonces aren't all spent, halt or not (the app asks you to tick a box before it lets you) |
| A DAO council loses its keys, or turns hostile | The contract obeys whichever account owns the satchel, so the DAO's policy is its whole defense. A council that can't pass a proposal leaves the satchel stuck; one with the votes can empty its address or take the satchel, since a Sputnik proposal runs on the vote that reaches its threshold | Give the council more members than its threshold needs. Proposals are public on NEAR, but where one member's vote reaches the threshold, as in the testnet DAO, a proposal can be filed and passed in one transaction, with no time to react. `nonceClash` in the library finds an open proposal that signs a nonce already in use |
| The holder is offline, during a swap through 1Click or at any time | Nothing in the Satchel contract acts on a timer. A satchel an estate contract owns is different: after missed check-ins, its guardians' approvals and a waiting period, it goes to the estate's heir. Mainnet satchel #2's quote named the satchel's own address as `refundTo`, so a refund, if 1Click's system sends one, lands back in the satchel with no step from the holder | Nothing. Let a swap end before you buy: the report doesn't count what is in flight |
| An RPC lies | A lying NEAR or EVM RPC can make a satchel look clean, or not. It can't change a satchel's address, derived from the MPC root key pinned in the package, or make `buy` take a record version other than the contract's | Run `satchel-nft verify` with `NEAR_RPC` and `RPC_<chain id>` set to nodes you trust ([RPCs, finality and rate limits](/docs/developers/rpc-and-finality)) |
| satchelnft.xyz is down | The contracts and the MPC network don't depend on it. The holder room's check runs on its server, so the room is shut too | Use the [CLI](/docs/developers/cli): `verify` builds the same report, and its sign commands sign with the near CLI's key. Any NEAR client can call the [contract](/docs/developers/contract) |

## Evaluate Satchel in 15 minutes

For a partner or a technical evaluator, without a wallet, a key or an account. You need Node.js 22 or later and git.

<Steps>

1. **Check both deployments against the chain.** From a clone of the repository, no install:

   ```bash
   git clone https://github.com/duongnq2798/satchel.git
   cd satchel
   node scripts/check-claims.mjs
   node scripts/check-claims.mjs --network mainnet
   ```

   You should see `13 of 13 claims hold` on testnet and `15 of 15 claims hold` on mainnet, each exiting 0. They read
   the contract's keys, code hash, NEP-330 metadata and MPC signer, the MPC root key the package derives addresses
   from and the keys it derives, the transactions that deployed and locked the Satchel contract,
   the calls it refused on testnet, satchel #1's first mainnet send on Base, and mainnet satchel #2's
   swap through NEAR Intents' 1Click, from Base to USDC on Arbitrum One.
   [Check every claim](/docs/security/check-every-claim#check-the-claims) says what each line reads.

2. **Run the report on a clean satchel and a cheating one.**

   ```bash
   npx -y satchel-nft@0.2.0 verify --network mainnet 1
   npx -y satchel-nft@0.2.0 verify 5
   ```

   The first reads `PROVABLY CLEAN` and exits 0; the second reads `NOT PROVABLE` and exits 1, on the pending check.

3. **Ask the chain without Satchel's code.** Two JSON-RPC reads with curl show the mainnet contract has no keys
   and runs the reproducible build:

   ```bash
   curl -s https://rpc.mainnet.fastnear.com -H 'content-type: application/json' -d '{"jsonrpc":"2.0","id":1,"method":"query","params":{"request_type":"view_access_key_list","finality":"final","account_id":"v1.satchel-nft.near"}}'
   curl -s https://rpc.mainnet.fastnear.com -H 'content-type: application/json' -d '{"jsonrpc":"2.0","id":1,"method":"query","params":{"request_type":"view_account","finality":"final","account_id":"v1.satchel-nft.near"}}'
   ```

   Look for `"keys":[]` and `"code_hash":"94x4MmZKXGetffqJJVePLTdFkJvsmeXRLmi74Mdp2Lph"`.

4. **Read the residual risks.** The [threat model's last section](/docs/security/threat-model#residual-risks-in-one-list)
   is the list of what Satchel does not stop. Decide which matter for your use.

5. **Optional: rebuild the wasm.** With Docker and cargo-near 0.22.0, check out `87148c6` and run
   `cargo near build reproducible-wasm` in `contracts/satchel`, then
   `node ../../scripts/code-hash.mjs target/near/satchel.wasm`. It should print the deployed code hash.
   [The reproducible build](/docs/security/check-every-claim#4-the-reproducible-build) has the steps, and how to
   download CI's own build instead.

</Steps>
