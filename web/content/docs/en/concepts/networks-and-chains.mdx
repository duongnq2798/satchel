Satchel runs on two NEAR networks, testnet and mainnet, each with its own contract and its own MPC
contract. Both contracts run the same code and can sign for the same 16 EVM chain ids. What differs is
which MPC network derives the keys, and so whether an address is safe for real value.

Each contract was deployed and initialized with its MPC contract in one transaction, so no one could
initialize it first with another signer. There is no admin and no method to change the MPC contract
later. The first check of every [report](/docs/concepts/clean-transfer-report) reads the contract's
access keys, code hash and `mpc_contract()` and compares them with these values, which the `satchel-nft`
package pins in its `config.ts` rather than trusting the contract to describe itself.

Token ids are per contract: satchel #1 on testnet and satchel #1 on mainnet are different tokens with
different owners and different addresses.

## The 16 chains

The contract's `SUPPORTED_CHAINS` holds 16 chain ids, the same on both networks. `sign_evm` refuses any
other with `Satchel: chain_id is not one of the supported chains`.

### Which chains you can send on

The contract would sign for any of the 16 on either network. The app and the CLI narrow that down:

- a **testnet** satchel sends only on the 8 **testnets**, from the app's testnet pages or `satchel-nft send`
  without `--network`;
- a **mainnet** satchel sends only on the 8 **mainnets**, from `/mainnet` pages or with `--network mainnet`.

So a testnet satchel never moves mainnet funds from the app or the CLI. The report, though, reads
every chain a record lists, whichever network it is on: a testnet satchel's record can name chain 1 if
someone called `sign_evm` directly, and the report checks it.

<Callout type="danger" title="Never send real funds to a testnet satchel's address">
The address is valid on every EVM mainnet, and the testnet contract can sign mainnet chain ids. But its
key is derived by NEAR's testnet MPC network, which is not meant to secure real value. Keep real funds in
mainnet satchels only, and only what you can afford to lose: Satchel is not audited.
</Callout>

### Why the list is fixed

A fixed list keeps every record checkable: the report knows an RPC and an explorer for every chain a
record can name. It also rules out signatures for chains that don't exist yet, whose transactions no one
could check today.

The cost is that the list can't change for the life of a contract. There is no admin, so
`SUPPORTED_CHAINS` can't gain a chain or drop a testnet that shuts down. A new chain needs a new contract,
deployed as a new account such as `v2.satchel-nft.near`. If a testnet in the list shuts down, a satchel
with history there can never read provably clean again, because its nonce can no longer be read.

Before it trusts an EVM node, the report checks that the node answers with the chain id it is configured
for; one that serves another chain counts as unreadable, never as a pass. In the CLI, `NEAR_RPC=<url>`
replaces the NEAR node and `RPC_<chain id>=<url>` replaces a chain's, for example `RPC_8453` for Base:

```bash
NEAR_RPC=https://<your-near-testnet-node> RPC_11155111=https://<your-sepolia-node> npx -y satchel-nft@0.3.0 verify 1
```

A `NEAR_RPC` that serves the other network stops the CLI with exit code 2. [RPCs, finality and rate
limits](/docs/developers/rpc-and-finality) covers running against your own nodes.

## Finality, chain by chain

Every EVM read in the report, a nonce or an allowance, is pinned to the chain's **finalized** block,
which can't be reorganized away. That is why a send shows up in a report only after a delay: about 13
minutes on Sepolia, and about 20 on Base, where mainnet satchel #1's first send read
`PROVABLY CLEAN` 21 minutes after it was broadcast. Until then the report reads
<Verdict v="unknown" />, not clean.

Aurora is the exception. Its RPC answers "finalized" with its latest block, so the report reads 10 blocks
further back there. Aurora's blocks follow NEAR's, which are final within a few blocks. The threat model
lists this as a residual risk: a chain whose RPC calls a non-final block finalized.
